> 10 轮全量循环 × 3 阶段（Review+Debug → Build → Test）
> 审计范围：workbench/ + .opencode/ + dist/ 示例项目
> 目标：从"能用"打磨到"精良"

## 执行规则

每轮严格按以下流程执行：

```
Phase 1: Review + Debug（只读审计 + 问题定位）
├─ explore: 读取相关代码，建立理解
├─ review: 按维度审计，输出问题清单
└─ debug: 定位根因，区分阻断/警告/建议

Phase 2: Build（针对性修复）
├─ 仅修复 Phase 1 标记的问题
├─ 每个修复必须有对应的审计项
└─ 不做无关重构，不做"顺便改进"

Phase 3: Test（验证修复 + 回归测试）
├─ 验证修复项确实解决原问题
├─ TypeScript 编译检查
├─ Vite 构建检查
└─ 回归：确认未引入新问题
```

## 轮次详细规格

### Round 1: 代码质量 — TypeScript 严格性与类型安全

**Review 维度：**
- `any` 类型使用（应为 0）
- 缺失的返回类型注解（公共函数必须显式声明）
- 缺失的参数类型注解
- 非空断言 `!` 使用（应极少或为 0）
- 类型守卫缺失（外部数据进入系统边界时）
- 枚举 vs 联合类型的选择一致性
- 泛型使用是否恰当

**Build 规则：**
- 逐项修复阻断和警告
- 每个修复保持功能不变
- 不引入新的 `any`

**Test 验证：**
- `tsc --noEmit` 零错误
- `vite build` 成功
- 修复前后功能行为一致

---

### Round 2: 架构一致性 — 模块边界与依赖方向

**Review 维度：**
- 模块间依赖方向（应为单向：shell → modules → bridge → server）
- 循环依赖检测
- 接口定义位置（应在 types.ts 或模块入口）
- 共享状态的访问模式（应通过 API，不直接 import 内部）
- 文件职责单一性（每个文件只做一件事）
- 命名一致性（同类功能使用相同命名模式）

**Build 规则：**
- 打破循环依赖
- 提取公共接口到 types.ts
- 拆分过重文件

**Test 验证：**
- 依赖方向正确
- 无循环依赖
- 所有 import 路径有效

---

### Round 3: 文心设计合规 — Token 使用与视觉一致性

**Review 维度：**
- 硬编码颜色值（应全部使用 `--wenxin-*` Token）
- 硬编码间距值（应使用 `--wenxin-space-*`）
- 硬编码字号（应使用 `--wenxin-text-*`）
- 字体栈一致性（应使用 `--wenxin-font-*`）
- 动效时长是否来自 Token（`--wenxin-duration-*`）
- 暗色模式映射完整性
- Accent 使用频率（全页 ≤ 2 处）

**Build 规则：**
- 替换所有硬编码值为 Token
- 确保暗色模式下 Token 正确映射

**Test 验证：**
- DevTools 中无硬编码值
- 暗色模式切换正常
- 视觉无明显变化

---

### Round 4: 无障碍 — WCAG 2.2 AA 合规

**Review 维度：**
- 所有交互元素的 `tabindex` 和键盘可达性
- `aria-label` / `aria-labelledby` 完整性
- 焦点指示器可见性（`:focus-visible` 样式）
- 颜色对比度（文字 ≥ 4.5:1，大文字 ≥ 3:1）
- 语义 HTML 使用（`<nav>`, `<main>`, `<button>` vs `<div onclick>`）
- 屏幕阅读器体验（`role` 属性、`aria-live` 区域）
- 键盘操作完整性（Enter/Space/Escape/Arrow）

**Build 规则：**
- 添加缺失的 aria 属性
- 修复对比度不足的颜色
- 确保键盘可操作

**Test 验证：**
- Tab 键可遍历所有交互元素
- 焦点指示器可见
- 对比度达标

---

### Round 5: 性能 — 加载与运行时效率

**Review 维度：**
- 首屏加载时间（目标 < 1s on localhost）
- CSS 文件大小（目标 < 50KB）
- JS bundle 大小（目标 < 100KB）
- iframe 加载策略（懒加载 vs 预加载）
- WebSocket 消息频率（是否有不必要的高频消息）
- DOM 操作频率（是否有不必要的 reflow）
- 内存泄漏检测（事件监听器是否正确移除）

**Build 规则：**
- 优化热路径
- 添加懒加载
- 移除不必要的 DOM 操作

**Test 验证：**
- 首屏加载时间改善
- 无功能回归

---

### Round 6: 错误处理 — 边界与降级

**Review 维度：**
- 网络请求失败处理（fetch 的 catch）
- 文件不存在处理（404 降级）
- iframe 加载失败处理
- WebSocket 断开重连
- JSON 解析失败处理
- 用户输入验证（XSS 防护）
- 错误信息用户友好性

**Build 规则：**
- 添加缺失的错误处理
- 实现降级策略
- 提供用户友好的错误信息

**Test 验证：**
- 断网场景不白屏
- 文件不存在有提示
- iframe 失败有降级

---

### Round 7: 状态管理 — 一致性与并发

**Review 维度：**
- 持久化数据与内存状态的一致性
- 多标签页同时编辑的竞态条件
- 状态更新的原子性（部分失败时是否回滚）
- 防抖/节流的正确性
- 状态恢复的完整性（刷新后是否丢失数据）
- 乐观更新与悲观更新的选择

**Build 规则：**
- 修复竞态条件
- 确保原子性
- 添加版本控制

**Test 验证：**
- 多标签页不冲突
- 刷新后数据完整
- 快速操作不丢失

---

### Round 8: 边界情况 — 极端输入与异常场景

**Review 维度：**
- 空项目列表（dist/ 为空）
- 单个项目
- 项目名包含特殊字符（中文、空格、emoji）
- 超大 HTML 文件（> 1MB）
- 超长批注文本
- iframe 内容为空或畸形
- 同时打开多个 Workbench 实例

**Build 规则：**
- 修复失败的边界测试
- 添加输入验证
- 添加大文件警告

**Test 验证：**
- 所有边界测试通过
- 极端输入不崩溃

---

### Round 9: 代码卫生 — 清理与规范

**Review 维度：**
- 死代码检测（未使用的函数、变量、import）
- 重复代码检测（相似度 > 80% 的代码块）
- 注释质量（是否有过时注释、TODO 清理）
- 命名一致性（同类功能使用相同命名模式）
- 文件组织（相关文件是否在同一目录）
- 导入顺序（是否一致：外部 → 内部 → 样式）

**Build 规则：**
- 删除死代码
- 提取重复代码为公共函数
- 统一命名模式
- 清理过时注释

**Test 验证：**
- 无死代码警告
- 无重复代码
- 功能无变化

---

### Round 10: 集成验收 — 端到端流程验证

**Review 维度：**
- 完整用户流程：启动 → 选择项目 → 预览 → 切换 viewport → 添加批注 → 导出 → 运行审计 → 查看状态
- 所有模块协作正常
- WebSocket 实时更新
- 文件监控自动刷新
- 暗色模式全流程
- 错误恢复全流程

**Build 规则：**
- 修复所有阻断项
- 处理关键警告
- 添加缺失的加载状态

**Test 验证：**
- 所有端到端流程通过
- 无阻断问题
- 警告 ≤ 3 项

## 回归保护

每轮 Test 阶段必须验证：

```bash
# 1. TypeScript 编译
cd workbench && npx tsc --noEmit

# 2. Vite 构建
cd workbench && npx vite build
```

**规则**：如果回归测试失败，本轮 Build 无效，必须回滚并重新修复。
