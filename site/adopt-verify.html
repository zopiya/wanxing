校验

24 门检查：仓库与产物检查、故障夹具反证，以及对真实公开契约的可运行查询。一个不可能失败的检查比没有检查更糟——它的绿色会被当成证据引用。

反向控制是这里的核心纪律

这个仓库有过三次"绿色掩盖真实缺陷"：

  • 审计矩阵读了一个从不存在的字段，每个示例都硬失败，而看板打印"0 failing"
  • 五个文字 token 不达 AA，最低 1.54:1，而当时没有任何检查测量过 token 数值
  • 对比度只对页面底色测，代码块在两个主题下都不合格，绿了整个仓库生命周期

三次的形状一样：检查没有洞，是检查的坐标系少了一维。 所以规矩是——你新加的每个检查，都要先故意制造它该抓的缺陷，确认它真的失败，再声称通过， 并在提交信息里写明怎么验的。

误报同样致命

check:components 的类名解析门第一次运行时把五个页面原型全报成未定义—— 它的 CSS 来源清单漏了 patterns/。比检查对象窄的检查器会产生误报， 而误报是让一道门被无视的最快方式。修好才敢用。

审计你自己的页面

完成本地安装后，在消费者项目根目录运行：

npm exec --no -- wenxin audit dist/<slug>/index.html

上面 24 门是这个仓库的自检，不会跑在你的页面上。 你的页面用 audit——它读同一份 token 真源，所以 token 一变，判定标准跟着变， 不会留下一份硬编码的副本慢慢腐烂。它只覆盖合同、DOM 与内联样式；外链 CSS、计算后样式、读屏器和五条判断规则仍须人工验证。

还没有被检查覆盖的

诚实记录比虚假的完整清单有价值：

  • 5 条需判断的规则——卡片几何、色块背景分区、强调色预算、填充主动作语义、装饰插画。原因见给 agent 用。
  • 窄屏渲染——已有最近一次本地 390px 手工走查，但尚未形成可复放的自动视觉回归基线。
  • forced-colors——Windows 高对比模式下这套依赖发丝线与墨色的语言表现如何，尚未实测。
